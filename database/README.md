## Состав

- `schema.sql` — новая схема `subscription_control`, девять таблиц, PK, FK, UNIQUE, NOT NULL, CHECK и индексы.
- `seed.sql` — два учебных пользователя, четыре категории, четыре подписки, шесть версий условий и примеры технических записей.
- `verify.sql` — 49 воспроизводимых проверок DB-01–DB-49 с допустимыми и намеренно недопустимыми операциями. Тестовые изменения откатываются.
- `examples.sql` — чтение данных, JOIN и точный расчет средней на фиксированную дату.
- `schema_meta.json` — словарь таблиц, полей и связей.
- `verification_manifest.json` — перечень проверок.
- `verification.csv` — фактические результаты выполненного прогона.
- `environment.csv` — версия СУБД и параметры отдельного проверочного соединения.
- `examples.csv` — фактический вывод нескольких запросов из examples.sql, с отдельным заголовком каждого результата.
- `traceability.csv` — связь 31 требования с компонентами, таблицами и тест-кейсами ОКФКС.
- `er_core.svg`, `er_technical.svg` — редактируемые ER-диаграммы основных и технических данных.

## Запуск

Нужен PostgreSQL 16 и клиент psql. Создайте отдельную новую учебную базу `pr6_verify` в своем PostgreSQL. Рабочую базу сервиса для этой практики не используйте. Скрипт структуры не содержит DROP и не заменяет существующую схему: повторный запуск в той же базе завершится ошибкой создания схемы.

Выполните команды из папки со скриптами. Передайте адрес сервера и учетную запись через `-h`, `-p`, `-U` либо переменные подключения. Пароль храните в защищенном файле подключения PostgreSQL, а не в SQL.

```text
psql -X -v ON_ERROR_STOP=1 -d pr6_verify -f schema.sql
psql -X -v ON_ERROR_STOP=1 -d pr6_verify -f seed.sql
psql -X -v ON_ERROR_STOP=1 --csv -d pr6_verify -f verify.sql -o my_verification.csv
psql -X -v ON_ERROR_STOP=1 --csv -d pr6_verify -f examples.sql -o my_examples.csv
```

Ожидается 49 строк со статусом PASS. Нарушения ограничений внутри verify.sql намеренные: ожидаемые SQLSTATE перехватываются и проверяются. Неожиданное принятие данных или другой SQLSTATE дают FAIL и завершают прогон с ошибкой. Последний ROLLBACK сохраняет исходные данные. Счетчики IDENTITY могут получить пропуски, поскольку последовательности PostgreSQL не откатываются; непрерывность ID не является требованием.

При повторной независимой проверке создайте новую учебную базу. Для будущего Django-приложения схема оформляется миграциями; текущие файлы не создают веб-интерфейс и не запускают системные тесты.

## Проверенный результат и границы

13.10.2026 скрипты выполнены в отдельном локальном PostgreSQL 16.15 на Windows: все 49 проверок прошли. Учебный сервер остановлен после прогона. Целевая среда приложения по архитектуре — Ubuntu 24.04 LTS и PostgreSQL 16.

Подтверждены структура, INSERT/SELECT/JOIN, уникальность, обязательность полей, FK, диапазоны, сохранение истории и технического ключа после удаления, условное обновление версии и откат связанных вставок. Проверка запросов БД не подтверждает исполнение системных TC-01–TC-25 из ОКФКС. Авторизация HTTP, обработка повторного запроса в C04, ограничения входа, CSRF, календарный алгоритм, браузеры, нагрузка, семь ежедневных копий и RPO/RTO требуют реализации и отдельных испытаний.

`subscription.owner_id` намеренно повторяет владельца категории для фильтрации и составного FK. Это ограниченная денормализация после проектирования до 3НФ, а не безусловное утверждение о строгой 3НФ всех физических таблиц. FK не заменяет проверку владельца при каждом чтении и изменении.

Открытые вопросы A-01–A-03 из предыдущей документации сохраняются: браузеры, три даты у границы 2100 года, реакция API на вторую версию с уже занятой датой. Уникальность даты версии проверяется БД; ответ интерфейса требует согласованного правила.
